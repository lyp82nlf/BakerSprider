# Barker 增量通知与数据抗抖设计

## 背景

Barker 接口在短时间内可能返回不同的数据集合或不同版本的字段值。当前监控程序把每一轮返回结果完整覆盖到本地快照，因此会产生两类误报：

1. 某个理财在一轮接口结果中临时缺失，下一轮重新出现时被误判为新增。
2. 利率或到期时间在两个接口版本之间来回切换，程序在两个方向上重复发送变化通知。

已观察到的典型抖动包括：

- Binance RLUSD 在 `8.46%` 和 `11.95%` 之间反向变化。
- Bybit USD1 在“长期”和固定到期时间之间反向变化。
- Gate GHO 在“长期”和固定到期时间之间反向变化。
- 相邻两轮出现两批近乎互补的“新增理财”。

实时采样确认 Barker 返回记录的 `pool_uid` 稳定，问题不需要通过重新定义理财唯一标识解决。

## 目标

- 只发送相对稳定基线已经确认的增量变化。
- 真正的新理财仍然发送通知。
- 单轮只有一个理财变化时，消息只包含这一项。
- 同一理财同时发生利率和到期变化时合并展示。
- 短时缺失、单轮尖峰、旧接口版本和字段往返抖动不产生通知。
- 兼容现有 `campaign_snapshot.json`，升级后不把全部存量理财误报为新增。
- 不改变抓取周期、利率阈值和每日理财日报的业务口径。

## 不在本次范围内

- 重新设计每日理财日报。
- 新增理财下架通知。
- 修改 Barker 接口或企微机器人配置。
- 根据收益率对理财作投资建议。

## 方案比较

### 方案 A：仅合并缺失记录

不再用本轮接口集合覆盖全部历史记录。该方案可以消除“临时缺失后重新出现”的新增误报，但不能阻止利率和到期时间反复跳变。

### 方案 B：稳定基线与连续两轮确认

将最新观测值、通知基线和待确认变化分开保存。变化连续两轮成立后才提交到通知基线并发送。该方案会带来约一个抓取周期的通知延迟，但能同时处理集合缺失和字段抖动。

### 方案 C：每轮请求三次并取多数值

同一轮请求接口三次并进行多数表决。该方案增加三倍请求量，可能触发限流；如果请求命中同一缓存副本，也不能证明数据稳定。

采用方案 B。

## 状态模型

监控状态分成三个层次：

1. **最新观测**：最近一次被接受的接口数据，用于本地列表和现有功能读取。
2. **稳定基线**：已经建立基线或已经成功通知的值，所有变化都相对它计算。
3. **待确认变化**：首次出现但尚未连续两轮成立的新理财、利率变化或到期变化。

状态同时保存：

- 最近接受的接口 `updated_at`。
- 同一接口版本的数据指纹。
- 每个理财最近出现的时间。
- 新理财的连续出现次数。
- 利率候选变化的方向和连续确认次数。
- 到期候选值和连续确认次数。

现有快照只有 `campaigns` 时，将这些理财直接作为稳定基线迁移，不生成新增事件。新状态字段使用向后兼容的可选结构，原有列表读取不受影响。

## 接口版本保护

每轮在事件检测前先检查原始记录中的 `updated_at`：

- 新版本晚于已接受版本：进入正常处理。
- 新版本早于已接受版本：整轮忽略，不更新快照、历史或待确认状态。
- 版本相同且数据指纹相同：视为一次有效的重复观测，可以用于连续确认。
- 版本相同但数据指纹不同：视为接口副本冲突，整轮忽略并记录警告。
- 接口没有有效 `updated_at`：不执行版本比较，但仍执行连续两轮确认。

数据指纹只基于规范化后的 UID、利率、到期时间和有效状态计算，不依赖接口返回顺序。

## 增量检测规则

### 新理财

1. 当前 UID 不在稳定基线时，创建待确认新增记录，次数记为 1。
2. 下一轮同一 UID 再次出现，次数加 1，并使用最新字段值。
3. 连续两轮出现后，发送一次新增通知并加入稳定基线。
4. 确认前任意一轮缺失，取消该待确认记录。
5. 新理财确认时不再额外生成利率或到期变化事件。

### 利率变化

1. 当前 APY 与稳定基线的差值绝对值达到现有阈值时，创建候选变化。
2. 下一轮仍达到阈值且变化方向相同，确认变化；最新 APY 作为通知终值。
3. 返回阈值以内或回到基线时，取消候选变化。
4. 变化方向反转时，旧候选取消，新方向从第一次观测重新计数。
5. 低于阈值的连续小变化以稳定基线为参照累计，达到阈值后再进入确认流程。

利率不要求两次浮点值完全相同，避免实时 APY 的正常小幅波动导致永远无法确认。

### 到期时间变化

1. 当前到期时间与稳定基线不同时，创建候选值。
2. 下一轮仍是同一个新到期值时，确认变化。
3. 返回基线或变成另一个候选值时，取消旧候选并重新计数。

### 临时缺失

- 稳定基线中的理财单轮缺失时保留，不生成事件。
- 缺失不会修改利率或到期候选，也不会被解释为下架。
- 连续 30 天未出现的记录从监控状态中清理；清理本身不通知。
- 待确认的新理财一旦缺失，立即取消待确认状态。

## 状态提交与通知失败

事件检测实现为一次状态转换：输入旧状态与本轮观测，输出事件和下一状态。

- 没有确认事件时，立即保存待确认计数和最新观测。
- 有确认事件时，先发送企微消息；发送成功后再提交对应稳定基线。
- 企微发送失败时不提交已经确认的基线变化，使下一轮能够重试通知。
- 状态文件采用临时文件替换方式写入，避免进程中断产生半写文件。

## 消息结构

消息只包含本轮已经确认的事件，不输出未变化的理财，也不附带完整列表。

单项利率变化示例：

```text
### Barker 理财变动

**Binance｜RLUSD**
APY：8.46% → 11.95%（↑3.49pct）
到期：2026-08-14 08:00
```

单项新增示例：

```text
### Barker 新增理财

**OKX｜RLUSD**
代币：RLUSD｜APY：10.00%｜到期：2026-08-20 23:59
```

同一理财有多个变化时：

```text
### Barker 理财变动

**Binance｜JustLend USDD**
APY：7.88% → 6.22%（↓1.66pct）
到期：2026-08-05 07:59 → 2026-09-05 07:59
```

同一轮有多个已确认事件时才展示多项，并按“新增、利率变化绝对值、到期变化”的优先级排序。同一理财只出现一次。

## 组件边界

- `client`：请求原始数据，不负责判断稳定性。
- `normalizer`：继续生成规范化理财对象，并提供接口版本信息所需的原始字段。
- `state`：持久化最新观测、稳定基线和待确认状态，负责旧格式迁移和原子写入。
- `monitor`：执行版本保护、连续确认和纯状态转换，不发送消息。
- `notifier`：按合并后的理财变化生成简洁 Markdown，不参与事件判断。
- CLI 主流程：协调抓取、检测、发送和成功后的状态提交。

## 测试要求

至少覆盖以下场景：

1. 旧快照迁移后不会把存量理财推送为新增。
2. 新 UID 只出现一轮时不通知。
3. 新 UID 连续出现两轮时只通知一次。
4. 稳定理财缺失一轮再出现时不通知。
5. 单轮利率尖峰后恢复时不通知。
6. 利率连续两轮同方向越过阈值时通知一次。
7. 利率在两个方向往返时不通知。
8. 到期时间单轮变化后恢复时不通知。
9. 到期时间连续两轮保持新值时通知一次。
10. 旧接口版本和同版本冲突数据被忽略。
11. 同一理财的利率和到期变化合并为一项。
12. 一轮只有一个事件时，模板中不出现其他理财。
13. 企微发送失败后，下一轮仍能重试同一个确认事件。
14. 状态文件写入中断不会破坏上一个完整状态。

## 验收标准

- 使用用户提供的两批交替数据顺序回放时，不再产生批量新增误报。
- `8.46% → 11.95% → 8.46%` 不产生利率通知。
- `长期 → 固定日期 → 长期` 不产生到期通知。
- 一个真实变化连续两轮成立时，只发送一条对应理财消息。
- 一个真实新理财连续两轮出现时，只发送一次新增消息。
- 全部现有测试和新增抗抖测试通过。
